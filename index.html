Tema uno

Control de versiones

Al terminar este módulo podrás: comparar modelos de control, describir el flujo de Git y elegir comandos de consulta y colaboración.

Definición

El control de versiones registra los cambios realizados en los archivos de un proyecto a lo largo del tiempo. Permite consultar versiones anteriores, comparar modificaciones y conocer quién hizo un cambio y cuándo. En un equipo, ayuda a que varias personas trabajen sobre el mismo código con menos riesgo de sobrescribir el trabajo de otras.

Un repositorio es el espacio donde se conserva el proyecto y su historial. Cada registro de cambios se denomina commit y suele incluir autor, fecha y una descripción breve.

Tipos de sistemas de control de versiones

Los tres modelos principales se diferencian por dónde guardan el historial y cómo colaboran sus usuarios. Recorre las pestañas con las flechas del teclado.

Control local (LVCS)

El historial se guarda en la computadora de una sola persona. Es sencillo y funciona sin red, pero depende de ese dispositivo y no facilita por sí mismo la colaboración. Algunas herramientas locales registran las diferencias entre versiones.

Control centralizado (CVCS)

Un servidor central conserva el historial común. Cada integrante obtiene una copia de trabajo y envía sus cambios al servidor. Simplifica la administración y los permisos, pero muchas operaciones dependen de la conexión y el servidor es un punto importante de disponibilidad. Ejemplos: Subversion (SVN) y CVS.

Control distribuido (DVCS)

Cada clon contiene una copia completa del historial. Se puede crear commits y ramas sin conexión y sincronizar más tarde. La colaboración es flexible y cada clon aporta una copia del historial; a cambio, requiere aprender conceptos adicionales y coordinar cómo integrar cambios. Ejemplos: Git y Mercurial.

Características, ventajas y desventajas

Comparación de los tres modelos de control de versiones
ModeloCaracterísticasVentajasDesventajas
Local Historial en una sola computadora. Fácil de iniciar y no necesita red. Sin colaboración integrada; la pérdida del equipo puede comprometer el historial.
Centralizado Un servidor conserva la historia compartida; los clientes usan una copia de trabajo. Permisos y estado común más simples de administrar. Dependencia de la red y del servidor para operaciones centrales.
Distribuido Cada clon conserva la historia completa del proyecto. Trabajo sin conexión, operaciones locales rápidas y ramas flexibles. Puede requerir más espacio y una curva de aprendizaje mayor.

Flujo de trabajo con Git

Git organiza los cambios en tres áreas locales y permite sincronizarlos con un remoto opcional. El remoto es útil para compartir y respaldar, pero no es necesario para crear commits locales.

  1. Directorio de trabajoEditas los archivos del proyecto.
  2. git addPreparar los cambios
  3. Área de preparaciónSeleccionas qué incluir en el próximo commit.
  4. git commitGuardar una versión
  5. Repositorio localSe incorpora el commit al historial local.
  6. git pushSincronizar con un remoto
  7. Repositorio remotoHistorial compartido alojado en un servidor.
Rama (branch)
Línea de trabajo independiente para desarrollar una función o corrección.
Merge
Integración de los cambios de una rama en otra; si hay conflictos, deben resolverse.
Pull
Obtiene cambios del remoto e integra los cambios según el comando empleado y la configuración.

Rastreo y gestión de cambios

  • git log consulta commits, autores y mensajes.
  • git diff compara cambios entre archivos, commits o áreas de trabajo.
  • git blame muestra el commit asociado a cada línea de un archivo.
  • Las ramas aíslan el trabajo y los tags identifican puntos importantes, como una versión publicada.
  • Una pull request (o solicitud de integración) permite revisar y conversar sobre cambios antes de incorporarlos; es una función de plataformas de alojamiento, no un comando propio de Git.
¿Es lo mismo Git que una plataforma de alojamiento?

No. Git es el sistema distribuido que gestiona versiones. Una plataforma de alojamiento puede guardar repositorios Git y ofrecer funciones adicionales, como revisión de cambios y seguimiento de tareas.

Ejemplos prácticos con Git

Este ciclo inicia un repositorio, prepara un cambio, lo guarda y consulta el historial. Para clonar un proyecto existente, reemplaza el marcador por la dirección que te proporcione tu equipo.

Terminal · ciclo básico
# Configurar identidad una sola vez en el equipo
git config --global user.name "Tu Nombre"
git config --global user.email "tu-correo"

# Crear un repositorio o clonar uno existente
git init
git clone <URL-del-repositorio>

# Revisar, preparar y guardar cambios
git status
git add archivo.js
git commit -m "Agrega una función"

# Crear y cambiar de rama
git switch -c nueva-funcion
git switch main
git merge nueva-funcion

# Consultar historial y diferencias
git log --oneline
git diff

Cuando se configura un remoto y existe permiso para publicar, git push envía los commits locales. No se debe ejecutar en un remoto desconocido o sin revisar su destino.

Preguntas frecuentes

¿Cada cuánto conviene crear un commit?

Cuando existe un conjunto pequeño y coherente de cambios que se puede describir con claridad. Los commits frecuentes y enfocados facilitan la revisión y la búsqueda de errores.

¿Un commit reemplaza una copia de seguridad?

No completamente. Un commit protege el historial local, pero una falla del dispositivo aún podría perderlo. Sincronizar con un remoto de confianza y mantener respaldos sigue siendo recomendable.

Persistencia y acceso a datos

Al terminar este módulo podrás: comparar opciones de persistencia, describir mecanismos de acceso y explicar un flujo de autenticación con tokens.

Definición y características

La persistencia permite conservar información después de que una aplicación se cierra. El acceso a datos comprende las operaciones para guardar, consultar, modificar y eliminar esa información. A diferencia de la memoria RAM, el almacenamiento persistente conserva los datos más allá de la ejecución actual.

Durabilidad e integridad

Los datos deben sobrevivir al cierre y mantenerse completos y coherentes, incluso ante operaciones concurrentes o fallos.

Disponibilidad y seguridad

La información debe poder consultarse cuando se requiere y protegerse con permisos y controles apropiados.

Rendimiento y sincronización

El acceso debe ajustarse a los recursos móviles; los cambios locales y remotos pueden sincronizarse cuando hay conexión.

Formas de persistencia en dispositivos móviles

Archivos y preferencias

Guardan datos como texto, JSON, XML, imágenes o documentos. El almacenamiento clave-valor (por ejemplo, preferencias de plataforma) es apropiado para opciones simples, como idioma o tema; no para secretos sin protección ni grandes conjuntos relacionados.

Útil para: preferencias, caché y documentos.

Bases de datos locales

Organizan datos estructurados en el dispositivo y permiten consultas y transacciones. SQLite es una base de datos relacional integrada en muchas plataformas; capas como Room proporcionan herramientas adicionales sobre SQLite.

Útil para: tareas, historial y funciones sin conexión.

Servicios y datos remotos

La app se comunica por una API con un servidor que autentica solicitudes y administra los datos compartidos. REST suele transportar recursos como JSON mediante HTTP; GraphQL permite solicitar campos específicos. Firebase ofrece varios servicios administrados, no un único tipo de base de datos.

Útil para: datos compartidos y sincronización entre dispositivos.

¿Qué opción funciona sin conexión?

Los archivos y bases de datos locales permiten trabajar sin red. Una aplicación también puede combinar almacenamiento local y remoto y sincronizar cambios más tarde, siempre que defina cómo resolver conflictos y conservar la consistencia.

Tipos de datos según la forma de persistencia

Ejemplos de información y almacenamiento adecuado

ArchivosTexto, JSON, XML, imágenes, audio, video y documentos.Documento descargado o archivo de configuración.Valida formato, tamaño y permisos.

Mecanismos de acceso a medios persistentes

Bibliotecas de clases

Las APIs de cada plataforma abstraen operaciones del sistema de archivos y preferencias. En Android se utilizan APIs de archivos y DataStore o preferencias; iOS ofrece FileManager y UserDefaults. Las credenciales y tokens deben guardarse en almacenes seguros del sistema, no en preferencias ordinarias.

Clases de SQLite

SQLite permite ejecutar consultas SQL en una base local. Usa parámetros en vez de concatenar texto para evitar errores de formato y ataques de inyección.

Ejemplo · SQL parametrizado
-- Crear una tabla sencilla
CREATE TABLE IF NOT EXISTS mascotas (
  id INTEGER PRIMARY KEY,
  nombre TEXT NOT NULL,
  especie TEXT
);

-- Insertar valores con parámetros enlazados desde la API
INSERT INTO mascotas (nombre, especie)
VALUES (?, ?);

-- Consultar los registros
SELECT id, nombre, especie FROM mascotas;

Mapeo relacional de objetos (ORM)

Un ORM conecta entidades del código con tablas de una base relacional. Reduce parte del SQL repetitivo y puede ofrecer migraciones y comprobación de tipos, pero no elimina la necesidad de entender consultas, transacciones y el diseño de datos. Room es una capa de persistencia de Android basada en SQLite.

Ejemplo conceptual · Kotlin y Room
@Entity(tableName = "mascotas")
data class Mascota(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val nombre: String,
    val especie: String
)

@Dao
interface MascotaDao {
    @Insert
    suspend fun insertar(mascota: Mascota)

    @Query("SELECT * FROM mascotas")
    suspend fun obtenerTodas(): List<Mascota>
}

Autenticación y consumo de servicios web

La autenticación comprueba quién realiza una solicitud. Un flujo habitual con una API usa HTTPS y un token de acceso de duración limitada. El servidor valida las credenciales; la app protege el token en el almacén seguro del sistema y lo envía en solicitudes autorizadas. Una respuesta 401 indica que la solicitud no está autenticada o que la credencial ya no es válida.

  1. La persona introduce sus credenciales en la aplicación.
  2. La app las envía al endpoint de inicio de sesión usando HTTPS.
  3. El servidor valida las credenciales y, si son correctas, emite un token.
  4. La app guarda el token de forma segura; no guarda la contraseña.
  5. Las solicitudes protegidas incluyen el token en el encabezado Authorization.
  6. El servidor valida el token y devuelve los datos o un error adecuado.
  7. La app maneja expiración, errores de red y estados de carga sin exponer secretos.

El siguiente fragmento es una plantilla ilustrativa: sustituye las rutas relativas por las rutas de una API de confianza. No realiza solicitudes al abrir este tutorial.

Ejemplo · Fetch y token
async function iniciarSesion(correo, contrasena) {
  const respuesta = await fetch('/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ correo, contrasena })
  });

  if (!respuesta.ok) {
    throw new Error('No se pudo iniciar sesión.');
  }

  const datos = await respuesta.json();
  return datos.token;
}

async function obtenerDatos(token) {
  const respuesta = await fetch('/datos', {
    headers: { Authorization: "Bearer " + token }
  });

  if (!respuesta.ok) {
    throw new Error('No se pudieron cargar los datos.');
  }

  return respuesta.json();
}
¿Puedo guardar el token en localStorage?

Para aplicaciones móviles nativas, utiliza el almacén seguro de la plataforma. En web, localStorage no es adecuado para secretos de autenticación frente a ataques de script; la estrategia debe elegirse según el modelo de seguridad de la aplicación.

Preguntas frecuentes

¿Qué datos deberían guardarse localmente?

Los necesarios para que la experiencia sea rápida o funcione sin conexión, con una política de retención clara. Evita almacenar datos personales innecesarios y protege la información sensible.

¿Qué hacer cuando los datos locales y remotos difieren?

Define una estrategia de sincronización explícita: por ejemplo, resolver conflictos por versión, registrar operaciones pendientes o pedir decisión a la persona usuaria. No existe una regla única adecuada para todas las aplicaciones.

Gestión de sensores

Al terminar este módulo podrás:reconocer sensores móviles y describir su habilitación, lectura, procesamiento y uso responsable en una app.

Definición y tipos de sensores

Un sensor es un componente físico o lógico que mide una propiedad del entorno o del dispositivo y entrega lecturas que el sistema operativo pone a disposición de las aplicaciones. Algunos sensores son piezas de hardware; otros, como la orientación o la ubicación, se calculan combinando varias fuentes. La presencia y precisión dependen del modelo del dispositivo.

Ejemplos de sensores y usos en aplicaciones móviles
Sensor o fuenteQué mide o estimaEjemplo de usoConsideración
AcelerómetroAceleración en los ejes del dispositivo, incluida la gravedad.Detectar movimiento o contar pasos con algoritmos adecuados.El ruido y la orientación afectan la lectura.
GiroscopioVelocidad angular y rotación.Control de cámara o movimiento en un juego.Puede acumular deriva; suele combinarse con otros sensores.
MagnetómetroCampo magnético.Apoyar una brújula digital.Interferencias magnéticas alteran las mediciones.
Proximidad y luzPresencia cercana a la pantalla e intensidad de luz.Apagar la pantalla durante una llamada o ajustar brillo.Disponibilidad y rango varían por dispositivo.
BarómetroPresión atmosférica.Estimación complementaria de cambios de altitud.No reemplaza una medición precisa de ubicación.
Ubicación (GNSS)Posición estimada por satélites y, según el sistema, otras fuentes.Mapa o navegación con permiso de ubicación.Requiere explicar el permiso y el uso de datos personales.

Privacidad: solicita solo los permisos necesarios, explica el propósito antes de pedir acceso y detén lecturas cuando ya no se necesitan. No todos los sensores requieren permiso de usuario, pero ubicación y actividad pueden estar protegidas por permisos específicos de la plataforma.

Proceso de gestión: habilitación, obtención y procesamiento

  1. Habilitar: comprobar si el sensor existe, solicitar permisos cuando corresponda y pedir al usuario que active servicios del sistema si son necesarios.
  2. Obtener información: suscribirse a lecturas con una frecuencia apropiada y conservar la marca temporal y las unidades del dato.
  3. Procesar: filtrar ruido, calibrar o combinar lecturas si el caso lo requiere; convertirlas en una decisión de aplicación.
  4. Finalizar: detener la escucha cuando la pantalla o tarea deja de necesitarla para cuidar batería y privacidad.
  1. ComprobarSensor y permiso disponibles
  2. registrarSuscribir un listener
  3. LeerValores y marca temporal
  4. procesarFiltrar o interpretar
  5. ActuarActualizar una función de la app
  6. detenerCancelar al salir del ciclo activo

Ejemplo de aplicación: lectura de acelerómetro en Android

Un juego puede inclinar un objeto con la aceleración en los ejes X e Y. El siguiente ejemplo es ilustrativo: se debe ejecutar desde el ciclo de vida de una pantalla y confirmar que el sensor existe. Para reducir consumo, se registra al reanudar la pantalla y se cancela al pausarla.

Kotlin · Android SensorManager
private val sensorManager by lazy {
    getSystemService(SENSOR_SERVICE) as SensorManager
}
private val acelerometro by lazy {
    sensorManager.getDefaultSensor(Sensor.TYPE_ACCELEROMETER)
}

private val listener = object : SensorEventListener {
    override fun onSensorChanged(event: SensorEvent) {
        val x = event.values[0]
        val y = event.values[1]
        // Actualizar el movimiento con valores filtrados si hace falta.
    }

    override fun onAccuracyChanged(sensor: Sensor?, accuracy: Int) = Unit
}

override fun onResume() {
    super.onResume()
    acelerometro?.let {
        sensorManager.registerListener(
            listener, it, SensorManager.SENSOR_DELAY_GAME
        )
    }
}

override fun onPause() {
    sensorManager.unregisterListener(listener)
    super.onPause()
}

La conversión de aceleración en una acción requiere definir umbrales y suavizado con pruebas reales; no conviene tratar una sola lectura como una decisión definitiva.

Uso de recursos multimedia

Al terminar este módulo podrás:distinguir tipos de medios, ubicar archivos en un proyecto y reconocer los componentes que los cargan, decodifican y presentan.

Definición y tipos de recursos multimedia

Los recursos multimedia son contenidos visuales, sonoros o animados que complementan la interacción de una aplicación. Deben elegirse en formatos adecuados a la plataforma, con dimensiones y calidad suficientes sin descargar más datos o consumir más memoria de la necesaria.

Medios habituales en aplicaciones móviles
TipoFormatos o tecnologíasEjemplo de aplicaciónCuidado de implementación
ImágenesJPEG, PNG, WebP, SVG para gráficos vectoriales compatibles.Fotografía de perfil, ilustraciones e iconos.Redimensionar y comprimir; cargar versiones apropiadas a la pantalla.
AudioAAC, MP3, OGG u otros formatos soportados por la plataforma.Voz, sonido de confirmación o narración accesible.Gestionar foco de audio, volumen y ciclo de vida del reproductor.
VideoContenedor y códec admitidos por el dispositivo; por ejemplo MP4 con H.264.Lección breve o evidencia de una actividad.Reproducción bajo demanda, subtítulos, red adaptable y liberación de recursos.
AnimacionesAnimaciones nativas, vectoriales o secuencias ligeras.Transición que indica que una acción concluyó.Evitar movimiento innecesario y respetar reducir movimiento.
Visuales dinámicosCanvas, gráficos, mapas y componentes de interfaz.Gráfica en tiempo real de sensores o progreso.Actualizar solo cuando cambian los datos y mantener contraste/alternativas.

Elementos del proyecto donde se almacenan los recursos

Los recursos empaquetados con la aplicación se organizan en carpetas específicas de cada plataforma. Los recursos descargados por el usuario se almacenan aparte, de acuerdo con permisos, disponibilidad y política de caché.

Android

app/src/main/res/drawable contiene imágenes y gráficos; res/mipmap se usa para iconos de lanzador; res/raw permite incluir archivos sin procesar. src/main/assets conserva archivos que la aplicación lee mediante AssetManager.

iOS

Los catálogos Assets.xcassets organizan imágenes, colores e iconos en variantes; otros recursos se incorporan al bundle del proyecto. Los permisos de cámara, micrófono o biblioteca se describen según el uso de la app.

Contenido remoto o del usuario

La caché y archivos generados deben tener una ubicación y política de borrado claras. No se debe incorporar contenido pesado al paquete si puede solicitarse de forma eficiente cuando el usuario lo necesite.

Componentes de software y ejemplo

Una función multimedia suele combinar varios elementos: una API de recursos, un decodificador adecuado, un componente de presentación y controles del ciclo de vida. Por ejemplo, ImageView presenta una imagen ya decodificada; Media3 ExoPlayer administra reproducción de audio/video en Android; AudioManager coordina volumen y foco de audio; Canvas o componentes declarativos dibujan visuales dinámicos. Apple proporciona APIs como AVFoundation. Cada componente debe pausarse y liberar recursos cuando corresponda.

  1. RecursoLocal o remoto
  2. cargarValidar ruta y permisos
  3. DecodificadorConvierte datos al formato de salida
  4. presentarVista o reproductor accesible
  5. GestionarPausa, memoria y ciclo de vida

Servicios y notificaciones

Al terminar este módulo podrás:explicar tareas en segundo plano, el acceso a datos mediante proveedores, el flujo de notificaciones y el papel de la nube.

Definición y tareas en segundo plano

Un servicio es un componente o mecanismo que permite a una aplicación realizar trabajo o exponer funciones sin depender directamente de una pantalla visible. Las tareas en segundo plano son operaciones que continúan fuera de la interacción inmediata, como sincronizar información, cargar una copia o procesar contenido. Los sistemas móviles limitan su duración y frecuencia para preservar batería, memoria y datos.

Elige el mecanismo según la tarea: trabajo diferible y reintentable se programa con APIs como WorkManager en Android; acciones breves vinculadas a una pantalla se ejecutan mientras esa pantalla está activa. No se debe asumir ejecución inmediata ni continua: el sistema puede aplazar tareas de acuerdo con restricciones de red, batería y versión del sistema.

Trabajo programado

Sincronización eventual con restricciones, estados de reintento y trabajo único.

Servicio en primer plano

Trabajo perceptible para el usuario, con notificación persistente y reglas específicas del sistema.

Trabajo de interfaz

Operaciones breves durante una pantalla activa; evita bloquear el hilo visual.

Ejemplo: programar una sincronización diferible

En Android, un trabajador implementa la operación y una solicitud define sus restricciones. WorkManager gestiona persistencia y reintentos, pero el momento exacto depende del sistema.

Kotlin · ejemplo conceptual con WorkManager
class SincronizarWorker(
    appContext: Context,
    parametros: WorkerParameters
) : CoroutineWorker(appContext, parametros) {
    override suspend fun doWork(): Result {
        return try {
            repositorio.sincronizarPendientes()
            Result.success()
        } catch (error: IOException) {
            Result.retry()
        }
    }
}

val restricciones = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.CONNECTED)
    .build()

val solicitud = OneTimeWorkRequestBuilder<SincronizarWorker>()
    .setConstraints(restricciones)
    .build()
WorkManager.getInstance(context).enqueueUniqueWork(
    "sincronizar-tareas",
    ExistingWorkPolicy.KEEP,
    solicitud
)

Proveedores de contenido

En Android, un ContentProvider ofrece datos mediante URIs y operaciones estándar de consulta, inserción, actualización y eliminación. El cliente normalmente accede con ContentResolver. El proveedor puede mediar el acceso a datos de otra aplicación, definir permisos y devolver un cursor; se debe solicitar únicamente el permiso que se necesita.

  1. Definir el tipo de datos, el URI y las operaciones que se exponen.
  2. Implementar operaciones con validación y permisos; aplicar consultas parametrizadas si se usa una base SQL.
  3. Declarar proveedor y controles de exportación en el manifiesto según corresponda.
  4. El cliente consulta mediante ContentResolver y cierra recursos después de usarlos.
Kotlin · consulta de un proveedor del sistema
val uri = MediaStore.Images.Media.EXTERNAL_CONTENT_URI
val columnas = arrayOf(
    MediaStore.Images.Media._ID,
    MediaStore.Images.Media.DISPLAY_NAME
)

contentResolver.query(uri, columnas, null, null, null)?.use { cursor ->
    while (cursor.moveToNext()) {
        val nombre = cursor.getString(
            cursor.getColumnIndexOrThrow(MediaStore.Images.Media.DISPLAY_NAME)
        )
        // Presentar el nombre sin exponer datos innecesarios.
    }
}

Los permisos de medios dependen de la versión de Android y del alcance de acceso. Prefiere selectores del sistema cuando la aplicación solo necesita que la persona elija archivos concretos.

Tratamiento e implementación de notificaciones

Una notificación comunica un evento fuera de la pantalla activa; no sustituye una interfaz ni debe incluir información sensible que pueda verse en una pantalla bloqueada. En Android se crean canales de notificación en versiones modernas; desde Android 13, muchas apps deben solicitar permiso de notificaciones. En iOS se solicita autorización al usuario y se configura el contenido y la entrega con UserNotifications.

  1. Definir un evento útil y un texto breve que explique qué ocurrió.
  2. Solicitar autorización en un contexto claro y respetar la decisión.
  3. En Android, crear un canal con categoría e importancia apropiadas; preparar una acción segura para abrir el contenido relacionado.
  4. En notificaciones remotas, registrar el dispositivo con el servicio y enviar desde un servidor autorizado; proteger credenciales de servidor.
  5. Al recibir la notificación, validar datos y dirigir a una pantalla permitida; ofrecer configuración y baja cuando aplique.
Kotlin · notificación local (canal creado previamente)
val notificacion = NotificationCompat.Builder(context, "recordatorios")
    .setSmallIcon(R.drawable.ic_notification)
    .setContentTitle("Recordatorio")
    .setContentText("Hay tareas pendientes de revisar.")
    .setPriority(NotificationCompat.PRIORITY_DEFAULT)
    .setAutoCancel(true)
    .build()

NotificationManagerCompat.from(context).notify(42, notificacion)

El ejemplo presupone que se creó el canal en Android 8 o posterior y que se obtuvo el permiso de notificaciones cuando la versión lo requiere. Para una acción al pulsar, agrega un PendingIntent explícito con comprobaciones de acceso apropiadas.

¿Una notificación remota es una tarea en segundo plano?

No. El servicio de notificaciones entrega un mensaje al dispositivo; la app puede procesarlo o mostrarlo según el sistema, permisos y estado. El mensaje no garantiza que se ejecute cualquier trabajo extenso; para trabajo diferible se usa el programador de tareas de la plataforma.

Servicios de cómputo en la nube y flujo de trabajo

La nube puede ofrecer APIs, bases de datos administradas, almacenamiento de objetos, autenticación, funciones bajo demanda y mensajería. Servicios como Firebase, Amazon Web Services y Microsoft Azure proporcionan distintos componentes; se seleccionan según privacidad, costos, disponibilidad, región, seguridad y portabilidad. La aplicación móvil no debe incluir claves privadas del servidor.

  1. AplicaciónAutentica a la persona
  2. HTTPSSolicitud autorizada
  3. API / funciónValida permisos y datos
  4. consultarReglas de acceso
  5. Datos en nubeBase, archivos o mensajería

Ejemplo: una app de tareas guarda cambios primero en la base local para que se puedan consultar sin red; un trabajador programado los sincroniza con una API autenticada cuando hay conexión. El servidor aplica autorización y devuelve el resultado, y la aplicación resuelve posibles conflictos.

Librerías y toolkits para desarrollo móvil

Al terminar este módulo podrás:diferenciar una librería de un toolkit y comparar conjuntos de herramientas nativos y multiplataforma.

¿Qué es una librería y qué es un toolkit?

Una librería es código reutilizable que ofrece funciones concretas; el programa la invoca cuando necesita una capacidad, como leer una base de datos o decodificar imágenes. Un toolkit es un conjunto coordinado de herramientas, APIs, bibliotecas y, en ocasiones, componentes de interfaz o compilación que facilita crear aplicaciones para una plataforma o grupo de plataformas.

Depuración y seguridad

Al terminar este módulo podrás:explicar cómo depurar fallos, reconocer herramientas del IDE móvil y aplicar controles básicos de seguridad durante todo el desarrollo.

Qué son la depuración y la seguridad

La depuración es el proceso sistemático de reproducir, observar y corregir defectos. Incluye examinar registros, detener la ejecución con puntos de interrupción, inspeccionar variables y probar la corrección. No se limita a eliminar errores de compilación: también verifica comportamiento, rendimiento, compatibilidad y experiencia de uso.

La seguridad protege la confidencialidad, integridad y disponibilidad de la aplicación y sus datos frente a errores, abuso o acceso no autorizado. Debe incorporarse desde el diseño y mantenerse en las actualizaciones. Una app móvil debe considerar el dispositivo, la red, los servicios remotos, las dependencias y los permisos del sistema.

Depurar para comprender

Un diagnóstico reproducible localiza la causa raíz y evita corregir síntomas que volverían a aparecer.

Proteger datos y usuarios

Reducir permisos, proteger secretos y validar acceso limita el impacto de fallos o configuraciones incorrectas.

Probar en contexto real

Emuladores y dispositivos físicos revelan diferencias de hardware, red, batería, tamaño de pantalla y versión del sistema.

Combina registros y herramientas de inspección con pruebas; elimina o desactiva registros de desarrollo que puedan revelar identificadores, tokens, contraseñas o datos personales.

Prácticas de seguridad y ejemplo

  • Solicitar permisos mínimos y explicar su propósito; permitir que la función opere sin permisos no esenciales.
  • Usar HTTPS, validar certificados mediante las APIs del sistema y autorizar cada operación en el servidor.
  • No incluir claves privadas ni credenciales de servidor en el paquete móvil; guardar tokens en el almacén seguro de la plataforma.
  • Validar entradas en cliente y servidor; usar consultas parametrizadas para bases de datos.
  • Actualizar dependencias y el SDK, revisar permisos y configuración de publicación, y probar errores y estados sin conexión.
  • Recolectar y conservar solo los datos necesarios; evitar mostrarlos en registros, notificaciones o analíticas no autorizadas.
¿El modo ofuscado hace segura una aplicación?

No por sí solo. La ofuscación puede dificultar la lectura del paquete, pero no sustituye la autorización del servidor, el almacenamiento seguro, el cifrado en tránsito ni la gestión correcta de permisos y secretos.

Ejemplo de registro útil para depuración: anota el tipo de fallo y un identificador de operación no sensible; nunca registres el token completo ni la contraseña.

Kotlin · registro sin secretos
try {
    sincronizarTareas()
} catch (error: IOException) {
    Log.e("SyncWorker", "Falló la sincronización de tareas", error)
    // Informar un estado comprensible sin incluir credenciales.
}

Para un marco de evaluación de seguridad móvil, consulta el estándar OWASP MASVS y las guías oficiales de seguridad de cada plataforma.

  1. ReproducirRegistrar pasos sin datos sensibles
  2. inspeccionarLogs, estado y permisos
  3. CorregirResolver causa raíz
  4. probarVerificar regresión y controles
  5. RevisarAnalizar y actualizar con seguridad
