Control de versiones

Definición

El control de versiones registra los cambios realizados en los archivos de un proyecto a lo largo del tiempo. Permite consultar versiones anteriores, comparar modificaciones y conocer quién hizo un cambio y cuándo. En un equipo, ayuda a que varias personas trabajen sobre el mismo código con menos riesgo de sobrescribir el trabajo de otras.

Un repositorio es el espacio donde se conserva el proyecto y su historial. Cada registro de cambios se denomina commit y suele incluir autor, fecha y una descripción breve.

Tipos de sistemas de control de versiones

Los tres modelos principales se diferencian por dónde guardan el historial y cómo colaboran sus usuarios. Recorre las pestañas con las flechas del teclado.

Control local (LVCS)

El historial se guarda en la computadora de una sola persona. Es sencillo y funciona sin red, pero depende de ese dispositivo y no facilita por sí mismo la colaboración. Algunas herramientas locales registran las diferencias entre versiones.

Control centralizado (CVCS)

Un servidor central conserva el historial común. Cada integrante obtiene una copia de trabajo y envía sus cambios al servidor. Simplifica la administración y los permisos, pero muchas operaciones dependen de la conexión y el servidor es un punto importante de disponibilidad. Ejemplos: Subversion (SVN) y CVS.

Control distribuido (DVCS)

Cada clon contiene una copia completa del historial. Se puede crear commits y ramas sin conexión y sincronizar más tarde. La colaboración es flexible y cada clon aporta una copia del historial; a cambio, requiere aprender conceptos adicionales y coordinar cómo integrar cambios. Ejemplos: Git y Mercurial.

Características, ventajas y desventajas

Comparación de los tres modelos de control de versiones
ModeloCaracterísticasVentajasDesventajas
Local Historial en una sola computadora. Fácil de iniciar y no necesita red. Sin colaboración integrada; la pérdida del equipo puede comprometer el historial.
Centralizado Un servidor conserva la historia compartida; los clientes usan una copia de trabajo. Permisos y estado común más simples de administrar. Dependencia de la red y del servidor para operaciones centrales.
Distribuido Cada clon conserva la historia completa del proyecto. Trabajo sin conexión, operaciones locales rápidas y ramas flexibles. Puede requerir más espacio y una curva de aprendizaje mayor.

Flujo de trabajo con Git

Git organiza los cambios en tres áreas locales y permite sincronizarlos con un remoto opcional. El remoto es útil para compartir y respaldar, pero no es necesario para crear commits locales.

  1. Directorio de trabajoEditas los archivos del proyecto.
  2. git addPreparar los cambios
  3. Área de preparaciónSeleccionas qué incluir en el próximo commit.
  4. git commitGuardar una versión
  5. Repositorio localSe incorpora el commit al historial local.
  6. git pushSincronizar con un remoto
  7. Repositorio remotoHistorial compartido alojado en un servidor.
Rama (branch)
Línea de trabajo independiente para desarrollar una función o corrección.
Merge
Integración de los cambios de una rama en otra; si hay conflictos, deben resolverse.
Pull
Obtiene cambios del remoto e integra los cambios según el comando empleado y la configuración.

Rastreo y gestión de cambios

  • git log consulta commits, autores y mensajes.
  • git diff compara cambios entre archivos, commits o áreas de trabajo.
  • git blame muestra el commit asociado a cada línea de un archivo.
  • Las ramas aíslan el trabajo y los tags identifican puntos importantes, como una versión publicada.
  • Una pull request (o solicitud de integración) permite revisar y conversar sobre cambios antes de incorporarlos; es una función de plataformas de alojamiento, no un comando propio de Git.
¿Es lo mismo Git que una plataforma de alojamiento?

No. Git es el sistema distribuido que gestiona versiones. Una plataforma de alojamiento puede guardar repositorios Git y ofrecer funciones adicionales, como revisión de cambios y seguimiento de tareas.

Ejemplos prácticos con Git

Este ciclo inicia un repositorio, prepara un cambio, lo guarda y consulta el historial. Para clonar un proyecto existente, reemplaza el marcador por la dirección que te proporcione tu equipo.

Terminal · ciclo básico
# Configurar identidad una sola vez en el equipo
git config --global user.name "Tu Nombre"
git config --global user.email "tu-correo"

# Crear un repositorio o clonar uno existente
git init
git clone <URL-del-repositorio>

# Revisar, preparar y guardar cambios
git status
git add archivo.js
git commit -m "Agrega una función"

# Crear y cambiar de rama
git switch -c nueva-funcion
git switch main
git merge nueva-funcion

# Consultar historial y diferencias
git log --oneline
git diff

Cuando se configura un remoto y existe permiso para publicar, git push envía los commits locales. No se debe ejecutar en un remoto desconocido o sin revisar su destino.

Preguntas frecuentes

¿Cada cuánto conviene crear un commit?

Cuando existe un conjunto pequeño y coherente de cambios que se puede describir con claridad. Los commits frecuentes y enfocados facilitan la revisión y la búsqueda de errores.

¿Un commit reemplaza una copia de seguridad?

No completamente. Un commit protege el historial local, pero una falla del dispositivo aún podría perderlo. Sincronizar con un remoto de confianza y mantener respaldos sigue siendo recomendable.

Tema dos

Persistencia y acceso a datos

Definición y características

La persistencia permite conservar información después de que una aplicación se cierra. El acceso a datos comprende las operaciones para guardar, consultar, modificar y eliminar esa información. A diferencia de la memoria RAM, el almacenamiento persistente conserva los datos más allá de la ejecución actual.

Durabilidad e integridad

Los datos deben sobrevivir al cierre y mantenerse completos y coherentes, incluso ante operaciones concurrentes o fallos.

Disponibilidad y seguridad

La información debe poder consultarse cuando se requiere y protegerse con permisos y controles apropiados.

Rendimiento y sincronización

El acceso debe ajustarse a los recursos móviles; los cambios locales y remotos pueden sincronizarse cuando hay conexión.

Formas de persistencia en dispositivos móviles

Archivos y preferencias

Guardan datos como texto, JSON, XML, imágenes o documentos. El almacenamiento clave-valor (por ejemplo, preferencias de plataforma) es apropiado para opciones simples, como idioma o tema; no para secretos sin protección ni grandes conjuntos relacionados.

Útil para: preferencias, caché y documentos.

Bases de datos locales

Organizan datos estructurados en el dispositivo y permiten consultas y transacciones. SQLite es una base de datos relacional integrada en muchas plataformas; capas como Room proporcionan herramientas adicionales sobre SQLite.

Útil para: tareas, historial y funciones sin conexión.

Servicios y datos remotos

La app se comunica por una API con un servidor que autentica solicitudes y administra los datos compartidos. REST suele transportar recursos como JSON mediante HTTP; GraphQL permite solicitar campos específicos. Firebase ofrece varios servicios administrados, no un único tipo de base de datos.

Útil para: datos compartidos y sincronización entre dispositivos.

¿Qué opción funciona sin conexión?

Los archivos y bases de datos locales permiten trabajar sin red. Una aplicación también puede combinar almacenamiento local y remoto y sincronizar cambios más tarde, siempre que defina cómo resolver conflictos y conservar la consistencia.

Mecanismos de acceso a medios persistentes

Bibliotecas de clases

Las APIs de cada plataforma abstraen operaciones del sistema de archivos y preferencias. En Android se utilizan APIs de archivos y DataStore o preferencias; iOS ofrece FileManager y UserDefaults. Las credenciales y tokens deben guardarse en almacenes seguros del sistema, no en preferencias ordinarias.

Clases de SQLite

SQLite permite ejecutar consultas SQL en una base local. Usa parámetros en vez de concatenar texto para evitar errores de formato y ataques de inyección.

Ejemplo · SQL parametrizado
-- Crear una tabla sencilla
CREATE TABLE IF NOT EXISTS mascotas (
  id INTEGER PRIMARY KEY,
  nombre TEXT NOT NULL,
  especie TEXT
);

-- Insertar valores con parámetros enlazados desde la API
INSERT INTO mascotas (nombre, especie)
VALUES (?, ?);

-- Consultar los registros
SELECT id, nombre, especie FROM mascotas;

Mapeo relacional de objetos (ORM)

Un ORM conecta entidades del código con tablas de una base relacional. Reduce parte del SQL repetitivo y puede ofrecer migraciones y comprobación de tipos, pero no elimina la necesidad de entender consultas, transacciones y el diseño de datos. Room es una capa de persistencia de Android basada en SQLite.

Ejemplo conceptual · Kotlin y Room
@Entity(tableName = "mascotas")
data class Mascota(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val nombre: String,
    val especie: String
)

@Dao
interface MascotaDao {
    @Insert
    suspend fun insertar(mascota: Mascota)

    @Query("SELECT * FROM mascotas")
    suspend fun obtenerTodas(): List<Mascota>
}

Autenticación y consumo de servicios web

La autenticación comprueba quién realiza una solicitud. Un flujo habitual con una API usa HTTPS y un token de acceso de duración limitada. El servidor valida las credenciales; la app protege el token en el almacén seguro del sistema y lo envía en solicitudes autorizadas. Una respuesta 401 indica que la solicitud no está autenticada o que la credencial ya no es válida.

  1. La persona introduce sus credenciales en la aplicación.
  2. La app las envía al endpoint de inicio de sesión usando HTTPS.
  3. El servidor valida las credenciales y, si son correctas, emite un token.
  4. La app guarda el token de forma segura; no guarda la contraseña.
  5. Las solicitudes protegidas incluyen el token en el encabezado Authorization.
  6. El servidor valida el token y devuelve los datos o un error adecuado.
  7. La app maneja expiración, errores de red y estados de carga sin exponer secretos.

El siguiente fragmento es una plantilla ilustrativa: sustituye las rutas relativas por las rutas de una API de confianza. No realiza solicitudes al abrir este tutorial.

Ejemplo · Fetch y token
async function iniciarSesion(correo, contrasena) {
  const respuesta = await fetch('/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ correo, contrasena })
  });

  if (!respuesta.ok) {
    throw new Error('No se pudo iniciar sesión.');
  }

  const datos = await respuesta.json();
  return datos.token;
}

async function obtenerDatos(token) {
  const respuesta = await fetch('/datos', {
    headers: { Authorization: `Bearer ${token}` }
  });

  if (!respuesta.ok) {
    throw new Error('No se pudieron cargar los datos.');
  }

  return respuesta.json();
}
¿Puedo guardar el token en localStorage?

Para aplicaciones móviles nativas, utiliza el almacén seguro de la plataforma. En web, localStorage no es adecuado para secretos de autenticación frente a ataques de script; la estrategia debe elegirse según el modelo de seguridad de la aplicación.

Casos de uso

  • Preferencias de tema e idioma: almacenamiento simple de clave-valor.
  • Lista de tareas que debe consultarse sin conexión: base de datos local.
  • Fotografías o documentos: archivos con permisos y límites de almacenamiento apropiados.
  • Publicaciones compartidas entre dispositivos: API y almacenamiento remoto con autenticación.

Preguntas frecuentes

¿Qué datos deberían guardarse localmente?

Los necesarios para que la experiencia sea rápida o funcione sin conexión, con una política de retención clara. Evita almacenar datos personales innecesarios y protege la información sensible.

¿Qué hacer cuando los datos locales y remotos difieren?

Define una estrategia de sincronización explícita: por ejemplo, resolver conflictos por versión, registrar operaciones pendientes o pedir decisión a la persona usuaria. No existe una regla única adecuada para todas las aplicaciones.
